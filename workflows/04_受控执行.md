# 03_受控执行 (Execution Sentry V2.1)

> **定位**: 核心生产环节。
> **目的**: 通过 **Evidence Block** 和 **Reverse Testing** 强制物理验证，消除"口头绿灯"。
> **V2.1升级**: 集成约束清单检查（01.5 规约形式化输出）

## Node A: 范围锁定与 Pack 加载 (Scope & Pack)

**指令**:
1. 锁定当前 Task 的 `Scope` (严禁越界修改)。
 - `Target_Files`: 仅允许修改的文件列表（来自 `/02_需求雷达` 的 Task_List / Target Files）
 - `Forbidden`: 本次不允许触碰的路径/资产（含 Solid-Strict/Regulated 的判定结果）
2. **原子化加载 `Pack-2` (Execution) `[K-BOOT]`**:
 - **仅加载**：由 `/02_需求雷达` 识别的目标修改文件（Target Files）。
 - **检索**：直接相关的 Interface/DTO，严禁全量装载整个模块目录。
 - **引用**：涉及的 `project-kernel/03_决策日志 (ADR).md` 条目。
3. **加载约束清单 `[K-CONSTRAINT]`** ← 新增
 - 从 `03_规约形式化` 获取约束清单
 - 从 `project-kernel/02_开发规约 (Specs)/` 获取项目规范
 - 加载 FSM 预期状态序列
 - 加载人工检查清单

## Node B: 原子执行 (Atomic Execution)

**执行原则 (Sentry Iron Rules)**:
1. **Patch-First**: 先输出 Diff 预览，后 Apply。
2. **Test-First**: 对于核心逻辑，先写 Test (Red) 再写 Impl (Green)。
3. **Reverse_Proof**: 核心算法/安全逻辑必须执行"破坏性证明" `[K-TEST]`（先人为制造红灯，再恢复绿灯）。
4. **Solid 保护**（以 `/02_需求雷达` 的 Solid_Touch 为准）:
 - 触碰 `Solid-Strict` -> **无 `Approval_Hash` 视为熔断**；Evidence 必须包含 `Approval_Hash` + `ADR_Entry` + `Asset_Update`。
 - 触碰 `Solid-Regulated` -> Evidence 必须包含 `ADR_Entry` + `Asset_Update`。
5. **约束实时检查** ← 新增
 - 每次 patch 后，对照约束清单进行快速检查
 - 重点检查 P0 级约束（强制）
 - **🆕 推荐使用脚本**: `./scripts/constraint-check.sh .`

## Node C.5: 约束检查（新增）

**指令**: 在生成 Evidence Block 后，立即执行约束检查

### 自动检查（快速扫描）

使用正则表达式或简单脚本快速检查：

```bash
# 示例：检查 Context Key 格式
grep -rn 'context\.put' src/main/java/... | grep -v 'node:'
# 如果有输出，说明存在违规

# 示例：检查是否继承 BaseAlgoComponent
grep -l 'extends BaseAlgoComponent' Target_Files
```

### 人工检查清单

对照 `03_规约形式化` 生成的检查清单，逐项验证：

```markdown
### ✅ 约束验证结果

#### P0 约束（强制）
- [x] Context Key 格式: node:{nodeId} ✅
 - 检查方式: grep context.put
 - 发现问题: 无
- [x] Context Value 类型: AlgoValue<T> ✅
- [x] 继承 BaseAlgoComponent ✅
- [x] 使用 @AlgoOperator 注解 ✅

#### P1 约束（建议）
- [x] 变量驼峰命名 ✅
- [ ] 方法注释完整 ⚠️ (可后续补充)

#### P2 约束（可选）
- [ ] 代码风格统一 (未检查)

#### 总结
- P0 违规: 0 ✅
- P1 警告: 1 ⚠️
- 状态: **通过**（P0 无违规）
```

### 违规处理流程

```
如果发现 P0 违规:
 → 标记为 Compliance_Status: 🔴 [Partial]
 → 必须修正后才能进入 04_质量关卡
 → 重新执行 Node B (原子执行)

如果发现 P1 警告:
 → 标记为 Compliance_Status: ⚠️ [Warning]
 → 记录警告，可继续流程
 → 在 05_归档重启 时决定是否修正

如果无违规:
 → 标记为 Compliance_Status: [Pass]
 → 进入 Node D (决策点)
```

## 使用技巧

### 快速约束检查命令

```bash
# 1. Context Key 格式检查
grep -rn 'context\.put' src/ | grep -v '"node:' | grep -v '//'

# 2. AlgoValue 类型检查
grep -rn 'context\.put' src/ | grep -v 'AlgoValue' | grep -v '//'

# 3. 继承关系检查
grep -l 'class.*Cmp' src/ | xargs grep -L 'extends BaseAlgoComponent'

# 4. 注解检查
grep -l 'class.*Cmp' src/ | xargs grep -L '@AlgoOperator'
```

### 常见 P0 违规及修正

**违规 1**: Context Key 格式错误
```java
// ❌ 错误
context.put("offset", value);

// ✅ 正确
context.put("node:timeOffset", value);
```

**违规 2**: Context Value 类型错误
```java
// ❌ 错误
context.put("node:result", rawValue);

// ✅ 正确
AlgoValue<Double> algoValue = new AlgoValue<>(rawValue, timestamp, quality, nodeId);
context.put("node:result", algoValue);
```

**违规 3**: 未继承基类
```java
// ❌ 错误
@AlgoOperator(code = "time_offset")
public class TimeOffsetCmp {
 // ...
}

// ✅ 正确
@AlgoOperator(code = "time_offset")
public class TimeOffsetCmp extends BaseAlgoComponent {
 // ...
}
```

## 常见问题

**Q: 每次都要手动检查清单吗？**
A: Level 1 是手动的。Level 2 会提供自动脚本。但即使手动，有清单也比依赖记忆好。

**Q: P1 警告可以忽略吗？**
A: 可以。P1 是建议性约束，不影响功能正确性。但建议在 05_归档重启 时集中处理。

**Q: 如果 P0 违规，必须立即修正吗？**
A: 是的。P0 是强制约束，违反会导致架构不一致或运行时错误。
