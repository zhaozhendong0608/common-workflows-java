# 03_规约形式化 (Constraint Formalization)

> **定位**: 架构规约的显式化与可检查化
> **目的**: 将隐式约束转化为显式检查清单，建立 FSM 映射基础
> **Level 1 补全**: 人工辅助版，实现 Sentinel-K 理论的"规约-FSM 映射引擎"雏形

## 执行时机

```
01_启动自检 (完成项目全景理解)
 ↓ ACK
02_需求雷达 (开始任务规划)
 ↓ ACK
03_规约形式化 (本阶段) ← 生成约束清单
 ↓ ACK
04_受控执行 (开始编码)
```

**何时执行**:
- 每次新开发会话，在需求雷达后立即执行
- 或在 02_需求雷达 识别出高风险任务时执行

## Node A: 提取核心约束规则

**指令**: 从以下文档中提取当前项目的架构约束

### 数据源
1. `project-kernel/02_开发规约/` (开发规约文档)
2. `09_算法编排专项开发.md` (算法编排约束)
3. `.cursorrules` (项目根目录配置)
4. 项目 README 或架构文档

### 约束提取格式

生成结构化的约束清单（YAML 格式）：

```yaml
# 项目架构约束清单
project: {PROJECT_NAME}
generated_at: 2026-06-23
version: 1.0

constraints:
 # 命名规范
 naming:
 - rule: "类名必须大写开头"
 level: P0 # P0=强制, P1=建议, P2=可选
 scope: "所有Java类"
 example: "TimeOffsetCmp, AlgoContext"

 - rule: "变量名驼峰命名"
 level: P1
 scope: "所有变量"
 example: "nodeId, algoValue"

 - rule: "算子类名必须以 Cmp 结尾"
 level: P0
 scope: "算法编排模块"
 example: "TimeWindowCmp, AnalogStatsCmp"

 # 架构约束
 architecture:
 - rule: "Controller 不能直接调用 Mapper"
 level: P0
 scope: "MVC 分层"
 rationale: "必须通过 Service 层调用"

 - rule: "算子 Context Key 必须是 node:{nodeId} 格式"
 level: P0
 scope: "算法编排模块"
 example: 'context.put("node:timeOffset", value)'
 anti_pattern: 'context.put("offset", value) ❌'

 - rule: "算子 Context Value 必须是 AlgoValue<T> 类型"
 level: P0
 scope: "算法编排模块"
 example: 'AlgoValue<Double> value = new AlgoValue<>(...)'
 anti_pattern: 'context.put(key, rawValue) ❌'

 - rule: "算子必须继承 BaseAlgoComponent"
 level: P0
 scope: "算法编排模块"

 - rule: "极生TDB必须使用 datasourceService.executeSql() 调用"
 level: P0
 scope: "数据访问层"
 rationale: "DBMS连接对象有状态，必须串行查询"

 - rule: "禁止极生TDB批量查询超过5个kids"
 level: P1
 scope: "性能优化"
 rationale: "批量查询展开为巨量Map对象，内存开销大"

 # 测试覆盖
 testing:
 - rule: "编译器测试覆盖率 >90%"
 level: P0
 scope: "算法编排 - 编译器模块"

 - rule: "算子测试覆盖率 >80%"
 level: P0
 scope: "算法编排 - 算子库"

 - rule: "核心算法必须有 Reverse_Proof"
 level: P0
 scope: "受控执行"
 explanation: "先破坏再恢复，确保测试有效"

 # 依赖约束
 dependencies:
 - rule: "编译器模块不允许依赖 Spring 容器"
 level: P0
 scope: "算法编排 - 编译器"
 rationale: "保持独立性，支持纯函数测试"

 - rule: "MyBatis Plus 租户插件需要 @InterceptorIgnore"
 level: P0
 scope: "无租户字段的表"
 example: '@InterceptorIgnore(tenantLine = "true")'
```

## Node B: 预测状态序列（FSM 规划）

**指令**: 对于当前开发任务，预测代码生成的状态转换序列

### FSM 状态序列格式

```yaml
# 当前任务的预期状态转换
task: "实现时间偏移算子 TimeOffsetCmp"
expected_states:
 - state: START
 description: "开始"

 - state: OPERATOR_DECL
 description: "算子类声明"
 must_include:
 - "@AlgoOperator 注解"
 - "extends BaseAlgoComponent"
 - "类名以 Cmp 结尾"
 must_complete_before: ["FIELD_DECL"]

 - state: FIELD_DECL
 description: "字段声明"
 must_include:
 - "@AlgoParam 注解的配置字段"
 must_complete_before: ["METHOD_DECL"]

 - state: METHOD_DECL
 description: "方法签名"
 must_include:
 - "process() 方法"
 must_complete_before: ["METHOD_IMPL"]

 - state: METHOD_IMPL
 description: "方法实现"
 constraints:
 - "使用 getUpstreamData() 获取上游数据"
 - "Context Key 必须是 node:{nodeId}"
 - "Context Value 必须是 AlgoValue<T>"
 - "使用 setOutput() 设置输出"
 must_complete_before: ["TEST_IMPL"]

 - state: TEST_IMPL
 description: "单元测试实现"
 constraints:
 - "测试覆盖率 >80%"
 - "包含正常流程和异常流程"
 must_complete_before: ["END"]

 - state: END
 description: "完成"
```

**人工审查点**:
- 确认状态序列是否完整
- 识别是否有跳步风险（例如直接写实现，跳过测试）

## Node C: 生成检查清单

**指令**: 将约束转化为人工检查清单（在 03_受控执行 完成后使用）

### 检查清单输出格式

```markdown
### ✅ 约束检查清单 - TimeOffsetCmp

生成时间: 2026-06-23
任务: 实现时间偏移算子

#### 命名规范
- [ ] 类名大写开头: TimeOffsetCmp ✅
- [ ] 类名以 Cmp 结尾 ✅
- [ ] 变量驼峰命名

#### 架构约束（算法编排）
- [ ] 继承 BaseAlgoComponent
- [ ] 使用 @AlgoOperator 注解
- [ ] Context Key 格式检查:
 - 查找所有 context.put() 调用
 - 验证格式: "node:{nodeId}"
 - 违规示例: "offset", "data" ❌
- [ ] Context Value 类型检查:
 - 所有 Value 必须是 AlgoValue<T>
 - 禁止裸对象或 Map
- [ ] 使用 getUpstreamData() 获取上游数据
- [ ] 使用 setOutput() 设置输出

#### 测试覆盖
- [ ] 单元测试已编写
- [ ] 测试覆盖率 >80%
- [ ] 包含异常流程测试

#### 状态序列验证
- [ ] OPERATOR_DECL 完成 (类声明)
- [ ] FIELD_DECL 完成 (字段声明)
- [ ] METHOD_DECL 完成 (方法签名)
- [ ] METHOD_IMPL 完成 (方法实现)
- [ ] TEST_IMPL 完成 (测试实现)
```

## 使用技巧

### 首次使用
1. 花 15-20 分钟仔细提取约束
2. 建立项目的"约束知识库"
3. 后续会话直接复用，只需微调

### 日常使用
1. 在 `01_启动自检` 后立即执行
2. 用 5 分钟快速生成检查清单
3. 将清单保存到剪贴板或临时文件

### 高价值场景
- 算法编排模块开发（约束最严格）
- 核心数据结构修改（影响面大）
- 多人协作项目（需要统一标准）

## 常见问题

**Q: 每次都要重新提取约束吗？**
A: 不需要。首次提取后，建立项目的约束知识库，后续只需复用并针对特定任务调整。

**Q: 状态序列预测有什么用？**
A: 帮助识别"跳步"风险。例如：AI 可能直接写实现，跳过测试。有了预期序列，可以在 Evidence Block 中验证是否完整。

**Q: 如果发现约束清单不够全怎么办？**
A: 在实际开发中遇到新约束时，随时追加到清单中。这是一个持续迭代的过程。
