## Node B: 计算 KVC (Key-Value Consistency)

> **KVC 定义**: 键值一致性，衡量代码是否符合命名规约
> **公式**: KVC = (符合规范的 Key 数量) / (总 Key 数量)
> **阈值**: KVC >= 0.90 (90%)

### Step 1: 搜索所有 Context Key

```bash
# 搜索所有 context.put() 调用
grep -rn 'context\.put' src/main/java/com/etl/station/algo/ > /tmp/context_calls.txt

# 查看结果
cat /tmp/context_calls.txt
```

### Step 2: 人工统计

逐行检查 `/tmp/context_calls.txt`，统计：

```markdown
### KVC 统计表

| 文件 | 行号 | Key | 是否符合 node:{nodeId} | 备注 |
|------|------|-----|---------------------|------|
| TimeOffsetCmp.java | 45 | "node:timeOffset" | ✅ | 符合 |
| TimeOffsetCmp.java | 52 | "node:result" | ✅ | 符合 |
| AnalogStatsCmp.java | 38 | "offset" | ❌ | 违规！缺少 node: 前缀 |
| AnalogStatsCmp.java | 55 | "node:maxValue" | ✅ | 符合 |

**统计结果**:
- 总 Key 数量: 4
- 符合规范: 3
- 违规: 1
- **KVC = 3 / 4 = 0.75 (75%)**
```

### Step 3: 判断是否达标

```markdown
### KVC 评估

- 计算值: 0.75
- 阈值: 0.90
- 状态: ❌ **未达标** (差距 15%)

#### 违规详情
1. AnalogStatsCmp.java:38
 - 当前: `context.put("offset", value)`
 - 应为: `context.put("node:offset", value)`

#### 修正建议
- 修改 AnalogStatsCmp.java 第 38 行
- 重新运行度量分析
```

## Node C: 计算 SCV (Structure Complexity Variation)

> **SCV 定义**: 结构复杂度变化，衡量代码复杂度的突变程度
> **公式**: SCV = |CC_current - CC_previous|
> **阈值**: SCV < 5.0

### Step 1: 计算修改前的复杂度（基线）

如果是首次开发，复杂度基线为 0。

如果是修改现有代码：
```bash
# 使用 git 检出修改前的版本
git stash
radon cc src/path/to/File.java -a

# 记录输出，例如: Average complexity: 3.5
```

### Step 2: 计算修改后的复杂度

```bash
# 恢复当前代码
git stash pop

# 计算当前复杂度
radon cc src/main/java/com/etl/station/algo/operators/TimeOffsetCmp.java -a
```

**示例输出**:
```
src/main/java/com/etl/station/algo/operators/TimeOffsetCmp.java
 M 45:4 TimeOffsetCmp.process - A (5)
 M 62:4 TimeOffsetCmp.validate - A (2)
 C 23:0 TimeOffsetCmp - A (7)
Average complexity: A (4.67)
```

### Step 3: 使用 lizard 获取圈复杂度

```bash
lizard src/main/java/com/etl/station/algo/operators/TimeOffsetCmp.java
```

**示例输出**:
```
NLOC CCN token PARAM length location
------ ------ ----- ----- ------ ------------------------------------------
 15 3 95 2 18 TimeOffsetCmp::process@45-62
 8 1 42 1 10 TimeOffsetCmp::validate@62-71
----------------------------------------------------------------
2 file analyzed.
==============================================================
NLOC Avg.NLOC AvgCCN Avg.token function_cnt file
------ -------- ------ --------- ------------ -------
 23 11.5 2.0 68.5 2 TimeOffsetCmp.java
```

**解读**:
- 平均圈复杂度 (AvgCCN): 2.0
- process 方法复杂度: 3
- validate 方法复杂度: 1

### Step 4: 计算 SCV

```markdown
### SCV 统计

#### 修改前（基线）
- 文件: TimeOffsetCmp.java
- 状态: 不存在（新文件）
- 复杂度: 0

#### 修改后（当前）
- 平均复杂度: 2.0
- 最高复杂度: 3 (process 方法)

#### SCV 计算
- CC_previous = 0 (新文件)
- CC_current = 2.0
- **SCV = |2.0 - 0| = 2.0**

### SCV 评估
- 计算值: 2.0
- 阈值: <5.0
- 状态: ✅ **正常** (复杂度稳定)
```

### Step 5: 趋势分析（可选）

如果是修改现有文件：
```markdown
### 复杂度趋势

| 版本 | 时间 | 平均复杂度 | SCV | 评估 |
|------|------|-----------|-----|------|
| v1.0 | 2026-06-01 | 3.5 | - | 基线 |
| v1.1 | 2026-06-15 | 4.2 | 0.7 | ✅ 正常 |
| v1.2 | 2026-06-23 | 8.5 | 4.3 | ⚠️ 接近阈值 |

#### 分析
- v1.1 → v1.2: SCV = 4.3，接近阈值 5.0
- 建议: 检查 v1.2 的修改，是否引入了过多分支逻辑
```

## 使用技巧

### 快速度量命令（一键执行）

创建脚本 `.agent/scripts/quick_metrics.sh`:
```bash
#!/bin/bash
TARGET_FILES="$@"

echo "=== KVC 检查 ==="
grep -rn 'context\.put' $TARGET_FILES | grep -v '"node:' | grep -v '//'

echo ""
echo "=== SCV 计算 ==="
for file in $TARGET_FILES; do
 echo "File: $file"
 lizard "$file" | tail -5
done
```

使用：
```bash
bash .agent/scripts/quick_metrics.sh src/main/java/com/etl/station/algo/operators/TimeOffsetCmp.java
```

### 常见度量场景

**场景 1**: 新文件开发
- CC_previous = 0
- 重点关注 CC_current 是否合理（建议 <10）

**场景 2**: 修改现有文件
- 对比修改前后的复杂度
- SCV 突增（>5）需要警惕

**场景 3**: 重构
- 期望 SCV 为负（复杂度下降）
- 如果 SCV 为正，说明重构可能引入了新逻辑

## 常见问题

**Q: 每次都要手动计算吗？**
A: Level 1 是手动的。Level 2 会提供自动脚本，秒级完成。

**Q: KVC 和 SCV 哪个更重要？**
A: 都重要。KVC 关乎架构一致性（P0），SCV 关乎可维护性（P1）。

**Q: 如果 SCV 超过阈值怎么办？**
A: 考虑拆分方法或重构逻辑。圈复杂度 >10 的方法通常难以维护。

**Q: 度量数据有什么用？**
A:
1. 当前：判断代码质量是否达标
2. 历史：追踪项目质量趋势
3. 对比：识别高风险模块（复杂度持续上升）

## 参考资料

### 圈复杂度阈值标准

| 复杂度 | 风险等级 | 可维护性 |
|--------|---------|---------|
| 1-10 | 低 | ✅ 简单，易于测试 |
| 11-20 | 中 | ⚠️ 中等，需要注意 |
| 21-50 | 高 | ❌ 复杂，难以维护 |
| >50 | 极高 | 🔴 极度复杂，建议重构 |

### KVC 阈值标准

| KVC | 评估 | 说明 |
|-----|------|------|
| 1.0 | ✅ 完美 | 所有 Key 符合规范 |
| 0.90-0.99 | ✅ 优秀 | 少量违规，可接受 |
| 0.80-0.89 | ⚠️ 警告 | 需要关注 |
| <0.80 | ❌ 不合格 | 必须修正 |
