## ADR-001: 选择 MyBatis 而非 JPA

**状态**: ✅ 已接受  
**日期**: 2025-01-10  
**决策者**: 张三  

### 背景
项目需要选择 ORM 框架，候选方案：MyBatis、JPA/Hibernate

### 决策
采用 MyBatis 作为 ORM 框架

### 理由
**MyBatis 优势**:
- ✅ SQL 完全可控，便于优化
- ✅ 支持复杂查询和动态 SQL
- ✅ 学习曲线平缓，团队熟悉
- ✅ 与时序数据库集成更灵活

**JPA 劣势**:
- ❌ 自动生成 SQL 难以优化
- ❌ 复杂查询需要写 JPQL
- ❌ 时序数据库支持较弱

### 后果
- ✅ 需要手写 SQL，工作量稍大
- ✅ 性能可控，便于调优
- ⚠️ 需要自行管理数据库变更（使用 Flyway）

## ADR-002: 采用 Caffeine 本地缓存

**状态**: ✅ 已接受  
**日期**: 2025-06-15  
**决策者**: 张三  

### 背景
首页数据查询耗时 4-5 秒（5 个月历史数据），需要优化。

候选方案：
1. 并行查询
2. Redis 集中缓存
3. Caffeine 本地缓存

### 决策
采用 Caffeine 本地缓存（TTL 60 秒）

### 理由
**测试结果**:
- 并行查询：反而增加 270ms 开销（线程调度成本）
- Redis 缓存：网络开销 10-20ms
- Caffeine 缓存：< 1ms，且无网络开销

**权衡**:
- ✅ 性能最优（< 1ms）
- ✅ 实现简单
- ⚠️ 缓存不一致窗口：60 秒（业务可接受）

### 实施
```java
@Cacheable(value = "homepage", key = "#deviceId", 
           cacheManager = "caffeineCacheManager")
public HomePageData getHomePageData(Long deviceId) {
    // ...
}
```

### 效果
- 首次查询：4-5 秒
- 缓存命中：< 100ms（减少 95%）

## ADR-003: 串行查询 TDB 而非批量查询

**状态**: ✅ 已接受  
**日期**: 2025-12-20  
**决策者**: 张三  

### 背景
极生 TDB 时序数据库查询策略选择

候选方案：
1. 批量查询（一次查询多个 kids）
2. 串行查询（逐个查询）

### 决策
采用串行查询 + 缓存

### 理由
**TDB 特性**:
- 批量查询虽然支持，但 SDK 会将结果展开为巨量 Map 对象
- 10 个 kids × 26 万点 = 269 万条记录，内存开销大
- SDK 的 DBMS 连接对象有状态，并发查询数据会混乱

**局域网环境**:
- 单次查询延迟 < 10ms
- 串行 70 次查询：约 700ms
- 加上缓存后，首次 4 秒，后续 < 100ms

**权衡**:
- ✅ 代码简单、数据准确
- ✅ 内存友好
- ✅ 配合缓存性能可接受
- ❌ 首次查询较慢（业务可接受）

## ADR-004: 报表模板支持算法模型多格式

**状态**: ✅ 已接受  
**日期**: 2026-01-15  
**决策者**: 张三  

### 背景
报表配置中的 `algoModel` 字段，用户输入方式不统一

### 决策
后端自动识别三种格式：
1. 算法模型 ID（数字）
2. algo_code（ALGO_ 前缀）
3. 算法名称（中文）

### 理由
- ✅ 提高用户体验（多种输入方式）
- ✅ 后端统一处理，前端无需关心
- ⚠️ 增加解析逻辑复杂度（可接受）

### 实施
```java
// 自动识别并查询算法模型
if (algoModel.matches("\\d+")) {
    // 数字 ID
    model = getById(Long.parseLong(algoModel));
} else if (algoModel.startsWith("ALGO_")) {
    // algo_code
    model = getByCode(algoModel);
} else {
    // 算法名称
    model = getByName(algoModel);
}
```

## ADR-005: 多机组报表采用方案 B（独立维度配置）

**状态**: ✅ 已接受  
**日期**: 2026-06-18  
**决策者**: 张三  

### 背景
算子评价规则功能，需要支持多个评价维度（准确性、稳定性、响应速度）

候选方案：
- **方案 A**: 多选 + 共享区间
- **方案 B**: 每个维度独立配置

### 决策
采用方案 B（独立维度配置）

### 理由
- ✅ 更灵活：每个维度可以有不同的评价区间
- ✅ 更清晰：配置界面直观
- ✅ 更易扩展：未来增加维度无需改表结构
- ⚠️ 数据量稍大（每个维度一条记录）

### 数据库设计
```sql
-- 唯一索引：一个模型 + 一个算子 + 一个指标 = 一条规则
CREATE UNIQUE INDEX uk_model_operator_metric 
ON fusion_operator_evaluation_rule(algo_model_id, operator_name, eval_metric);
```
